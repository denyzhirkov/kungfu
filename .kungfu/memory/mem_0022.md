CONVENTION (v2.5.20): every persistence write in `kungfu-storage` MUST go through the private `atomic_write(path, contents)` helper — write a sibling temp file (`.<name>.<pid>.tmp`) then `std::fs::rename` over the target. Rename is atomic on the same filesystem, so a crash/power-loss mid-write leaves the previous file intact instead of a truncated, unparseable one. Never call `std::fs::write` directly for a store file again.

Why it mattered: before v2.5.20 all 7 save_* fns used raw `fs::write`. The CLAUDE.md storage invariant claims "Atomic write via tmp + rename" but it was unimplemented. Most acute for `project_memory.json` (the hand-curated [[mem_0021]] manual memory layer) — unlike index shards it CANNOT be rebuilt by reindex, and the access pattern is read-all-before-every-op, so a single truncated file takes the entire manual memory offline.

Scaling note on project memory: `project_memory.json` is one pretty-JSON array, read-parsed and rewritten in full on every add/update/remove/search (no in-memory cache, unlike memories.json). O(N) per op, O(N²) over project lifetime; `archive` only flips status (never shrinks the file). Realistic size after a year is sub-MB to a few MB (text), NOT gigabytes — fine for now. Only revisit (compaction of archived / month sharding / append-log) if it ever reaches tens of MB. YAGNI until then.
