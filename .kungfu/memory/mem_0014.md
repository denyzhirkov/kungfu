КРИТИЧЕСКИЙ БАГ (найден при проверке живого MCP, исправлен v2.5.11): index_incremental перестраивал relations ТОЛЬКО из переизменённых файлов через build_relations(&new_files, &all_imports)+build_call_relations(...), где all_imports/all_calls собираются лишь для re-parsed файлов. При no-op реиндексе (контент не менялся, только mtime) all_imports/all_calls пусты → relations.json становился `[]`. Весь граф (imports + calls) обнулялся.

ТРИГГЕР: MCP service() на каждом вызове зовёт ensure_fresh_index(); та считает индекс stale, если любой файл под crates/src/... новее fingerprints.json (а при активной разработке так почти всегда) → запускает index_incremental → граф обнулялся. Симптом: callers/callees отдают call_graph_not_indexed сразу после успешного `kungfu index --full`.

Это был PRE-EXISTING баг (imports страдали так же), но call-граф сделал его заметным.

ФИКС: index_incremental теперь МЁРЖИТ как index_only — грузит old_relations, собирает changed_file_ids (id переизменённых файлов), оставляет старые relations, чей source НЕ из изменённого файла (и file-level source_id, и symbol-level по префиксу `s:{fid}:`), и добавляет свежие для изменённых. Регресс-тест: incremental_with_no_changes_preserves_relations.

ОСТАЁТСЯ ПОХОЖИЙ БАГ (не исправлен, отдельно): index_incremental так же перестраивает memories=build_memories(&all_comments) только из re-parsed файлов → comment-derived memories (TODO/FIXME/doc) обнуляются при no-op реиндексе. Project-memory (memory_add) в отдельном store, не затронут. Нужен такой же мёрж old_memories по changed paths. Завести задачу.

Замена бинаря: cp в .new + mv -f (atomic, иначе ETXTBSY/SIGKILL — старый процесс держит mmap). Уже запущенный харнессом MCP-процесс НЕ перецепляется в рамках сессии — нужен реконнект MCP, чтобы mcp__kungfu__* увидели новый бинарь.
