RECURRENCE of mem_0009 index-blowup, on the sibling `ecosystem` project, v2.6.1 (2026-07-21). Symptom the user reported: "kungfu MCP hangs when accessed in ecosystem." Root: `.kungfu/index/symbols.json` = **10 GB / 23,129,915 symbols** (clean is 4.4 MB / 12,144). Stack of the hang: `SearchEngine::search_text` -> `JsonStore::symbols_arc` -> `process_cache::Slot::get_or_load` -> `std::fs::read_to_string` -> `from_utf8` — i.e. slurping + UTF-8-validating the 10 GB shard, ~30% CPU for minutes. ANY of the 6 live `kungfu mcp` servers that served a tool call on ecosystem wedged there.

WHAT IT IS (and isn't): duplicate ACCUMULATION, not a parser explosion. Offender file `packages/shared/src/queues.ts` (a normal 24 KB / 512-line valibot schema) appeared **316,634×** in just the first 300 MB. Proven innocent: indexing queues.ts in an isolated temp project → 86 symbols, 33 KB. So mem_0009's byte-cap (`max_file_bytes`, 2 MiB) correctly didn't fire — the file is tiny — and the deferred PER-FILE SYMBOL CAP is exactly what was missing (mem_0009: "revisit if a sane-sized file ever blows up the index again" — this is that day).

NEW EVIDENCE vs mem_0009: a SECOND copy of queues.ts was indexed under an ABSOLUTE PATH OUTSIDE THE PROJECT ROOT — `/private/tmp/claude-501/.../scratchpad/rt-wt/packages/shared/src/queues.ts` (a git-worktree agent's copy, "rt-wt"), also ~316K dupes. So a worktree-agent session leaked external absolute paths into the index, and each path accumulated symbols without eviction. mem_0009 claimed the 2.5.5 watcher/dedup fix closed this class — it did NOT under the worktree-agent path. The `rt-wt` scratchpad and any extra git worktree were already gone by the time of diagnosis, so the accumulation source was dormant → clean reindex is stable.

FIX APPLIED (immediate, user side): `mv .kungfu/index aside; mkdir -p .kungfu/index; kungfu index --full` → 4.4 MB / 12,144 symbols; `search "crashbox"` 39 ms. Deleted the 10 GB backup. NOTE: `kungfu index --full` needs `.kungfu/index/` to already EXIST (atomic_write writes a sibling .tmp into it) — renaming the dir away and reindexing fails with "writing temp file ...: No such file or directory"; recreate the dir first. Live MCP servers self-heal via the mem_0024 stamp check (atomic rename → new inode → reload) — no MCP restart needed.

ENGINE GAPS (task created, see tsk): (1) per-file symbol cap; (2) reject indexing absolute paths outside project root; (3) reproduce the no-eviction accumulation trigger under worktree/reindex loops; (4) read-side guard so a pathological shard degrades loudly instead of hanging in read_to_string.
