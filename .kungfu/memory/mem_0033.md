Root cause of the mem_0009 / mem_0032 index blow-up (10GB symbols.json, MCP hang) FOUND and FIXED in v2.6.2. Closes tsk m7321p (essential layers).

EXACT MECHANISM (reproduced deterministically): `file_id = format!("f:{}", &blake3(CONTENT)[..12])` — a CONTENT hash. Two tracked files with byte-identical content at different paths (in `ecosystem`: `apps/backoffice/vitest.config.ts` == `packages/ui/vitest.config.ts`) collide on one file_id. Then `index_incremental`/`index_only` rebuild symbols by copying `old_symbols.filter(|s| s.file_id == entry.id)` ONCE PER PATH-ENTRY (keep-loop iterates every old_files row / .find()s per path). With 2 path-entries sharing a file_id, each copies BOTH sets → the symbol set DOUBLES every reindex. Driver: MCP `ensure_fresh_index` runs incremental on every tool call; 6 live servers → 4.4MB→10GB in ~6min. Proven: symbols 7→13→25→49→97→193→385 across successive `index --only` on an UNRELATED file; ~18 doublings → 300K+ copies of one file.

THE FIX — 3 independent nets (defense-in-depth, user chose this over a file_id identity rework):
1. DEDUP ON SAVE (the load-bearing one). `kungfu-storage::save_symbols` dedups by `Symbol.id`, `save_files` by `path`, via `dedup_by()` (first-wins, order-preserving). Symbol id = `s:{file_id}:{line}:{name}` — a duplicate id is definitionally the same logical symbol, so collapsing is correct and permanently kills the doubling regardless of trigger. Single chokepoint for all 3 index paths (full/incremental/only).
2. PER-FILE SYMBOL CAP (mem_0009's long-deferred backstop). Config `[index] max_symbols_per_file` (default 10_000). `index_file_with_content` truncates + `warn!`s a byte-sane file that emits a pathological symbol count (the byte cap `max_file_bytes` can't catch a small file). Bounds any FUTURE amplifier.
3. READ-SIDE SHARD GUARD (never hang again). `process_cache::get_or_load` bails BEFORE `read_to_string` if a shard exceeds `MAX_SHARD_BYTES` (1 GiB const) with "…is corrupt (duplicate-symbol accumulation). Rebuild with `kungfu index --full`." So any future corruption fails loud with a fix hint instead of wedging every MCP server on a 10GB slurp.

VERIFICATION: unit test `save_symbols_dedups_by_id` + `dedup_by_keeps_first_per_key_preserving_order` (kungfu-storage). Live: ecosystem reindexed 12144 symbols/4.4MB, stays FLAT through 10× `index --only` on the seed file + a full incremental (before: one incremental doubled it). Full gate green (fmt/clippy/44+ test groups). Deployed to /Users/denis/.local/bin/kungfu @2.6.2 (rm+cp).

NOTE — the deeper root (content-hash file_id conflates identical-content files) is NOT changed; dedup makes it harmless (identical files' symbols share ids → collapse to one set, acceptable). Path-based file_id remains the elegant follow-up (schema bump + reindex migration) if identical files ever need distinct symbol listings — deferred. Still-running MCP servers from other sessions hold the OLD (buggy) binary until reconnect (mem_0014) — restart to pick up 2.6.2. Links [[mem_0009]] [[mem_0032]] [[mem_0014]] [[mem_0024]].
