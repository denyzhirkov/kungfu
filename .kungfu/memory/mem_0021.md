INVARIANT for any snippet/excerpt/signature extraction: never slice a string or line-Vec by a raw byte index or by an index derived from an indexed span without guarding.

Two failure modes, both shipped as panics on Windows user repos (fixed in v2.5.18 / v2.5.19):

1. UTF-8 boundary panic. Slicing a String by a fixed byte length (`&s[..max_len]`) lands inside a multi-byte char (e.g. Cyrillic 'т' = 2 bytes) → "byte index N is not a char boundary". Fix: walk down to the nearest boundary — `while end > 0 && !s.is_char_boundary(end) { end -= 1; }` then `&s[..end]`. See `kungfu-parse::first_sentence` (lib.rs).

2. Stale-span OOB / overflow. A span (start_line/end_line) cached at index time can point past the current file if the file shrank. `end.min(lines.len())` bounds end but NOT start; in release builds `end_idx - start_idx` wraps (no debug overflow check) and `lines[start_idx..start_idx+take]` panics "range start out of range". Fix: guard BOTH ends before slicing — `if start_idx >= lines.len() || end_idx <= start_idx { continue/return }`. See `kungfu-core::ask.rs` (the bug), `edit.rs` and `explore.rs::symbol_snippet` (already correct — copy their pattern).

Safe-by-construction (no guard needed): byte offsets from tree-sitter `node.start_byte()..end_byte()` (always on boundaries, within source); indices from `.find()` (valid boundaries); `%H` git hashes (always 40 hex); `.chars().take(n)`; `Vec::truncate`. Audit of all crates (2026-06-24) found no other unguarded sites.
